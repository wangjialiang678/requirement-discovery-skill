# 低负担访谈与结构化选项

用于用户只有一句模糊问题、明确不想长篇输入，或宿主提供结构化提问界面的场景。目标是降低**作答**成本，而不是降低问题的信息密度；用户点选前应理解为什么这样分、选择会影响什么，同时不能替用户编造原因与判断。

## 按输入信息量启动

| 输入状态 | 第一轮动作 |
|---|---|
| 只有一句宽泛问题 | 简短说明目的与退出方式，然后用一道结构化选择题定位范围 |
| 已描述具体症状 | 直接定位症状发生的环节、对象或时间，不再索要“公司背景介绍” |
| 已有案例或数据 | 追当前最高价值未知项，不重复路由 |
| 用户表示“不知道” | 提供对比选项、典型情境或“不确定”，让其做识别而非创作 |
| 用户主动长篇表达 | 接住自由倾倒，之后再单题追问 |

不要用“请介绍行业、规模、目标、尝试和困难”作为一句话输入后的第一轮。这把访谈负担全部转嫁给用户。

## 什么时候给选项

适合结构化选择：

- 本轮要决定进入哪个问题分支；
- 定位问题发生在哪个流程阶段；
- 从用户已经提到的多个方向中选优先项；
- 询问低敏感、用户能直接识别的事实类别；
- 用户卡住、希望获得提示或明确要求少打字。

保持开放式：

- 为什么这件事重要；
- 什么结果不可接受；
- 愿意牺牲什么；
- 对人、文化、品牌和风险的价值判断；
- 索取一个真实案例、关键事件或隐性判断理由。

## 选项质量

本节的格式约束高于“介绍访谈”“复述上一答案”等一般对话习惯。结构化选择轮正文留空，题号、判断框架和唯一问题全部放进工具的 `question` 字段，避免解释与问题分散在两个消息通道。

- 一道完整的结构化问题由三部分组成：**题号和紧凑判断框架 → 一个问题 → 带解释的选项**，三部分都位于同一张结构化问题卡中。
- 工具 `question` 固定写成 `【问题 N/总数】判断框架。唯一问题？`，最后一个字符必须是中文问号。判断框架控制在约 60–140 个汉字、两三句：给一个有用但不过度承诺的分析视角，说明为什么这个分叉会改变后续判断，并指出这只是定位入口而非根因结论。
- 正文留空。问题卡不复述用户刚才点了什么，不罗列可能原因或解决方案，不出现状态名或内部账本；不用 Markdown 标题、粗体、分隔线、角色自我介绍、客套话、停止说明和仪式化开场。整轮只能出现一个问号。
- 一题只解决一个路由变量。
- 通常给 3–4 个平行选项。宿主自动提供“其他”时不要重复添加；宿主不会自动提供时，把最后一项设为“不确定 / 其他”，总数仍尽量不超过 4。
- 标签用用户语言描述可识别的情形，不使用内部框架术语。描述优先交代什么可观察现象符合它；确有必要时再用半句说明下一轮关注方向，通常为 20–50 个汉字。
- 标签优先写可观察现象、行为、任务或流程阶段，不把“管理跨度太大、激励不足、战略不清”等诊断性原因做成让用户点头的选项。
- 选项应尽量覆盖常见分支并互相区分；若允许多选必须明确写出。
- 不把某个选项标成推荐，也不暗示“不选它就是落后”。
- 用户选择后先记录为 `STATED`，不能当成已证明的根因。
- 工具的所有字段使用纯文本；标签和描述中禁用中文或英文引号，不使用 Markdown、换行或嵌套列表，确保宿主能解析结构化参数。
- 使用结构化提问工具时，工具的 `question` 字段必须直接写成 `【问题 N/总数】判断框架。唯一问题？`，正文不再重复任何部分。若宿主原生提供独立的背景字段，可把判断框架放入该字段，但仍须保证它与问题显示在同一张卡中。
- 连续选择题通常不超过两轮。选择适合快速定位，真实案例与隐性判断仍需要一条短开放回答；可以要求“用一两句话说最近一次发生的情况”，而不是再次索要完整背景。
- 普通轮次不显示 `STATED`、`asked_count` 等内部状态名。索取案例时只问一个事件，例如“最近一次出现这种情况时发生了什么？一两句话即可”，不要在一句里再要求人物、任务、耗时和影响等多个字段。

## 输出前自检

结构化选择题发出前检查：

1. 正文是否为空；
2. 工具 `question` 是否包含足够的判断框架、只问一个问题，并以正确题号开头；
3. 是否有 3–4 个实质分支，且每项有可观察解释；
4. 宿主自动提供“其他”时，是否没有重复的“其他”选项；
5. 整轮是否没有推荐、根因断言或具体解决方案。

生成时先在内部写好问题与选项，再把题号、判断框架和唯一问题合并到工具 `question` 中，直接调用工具；不要先输出正文。

若任一工具参数无法构造为合法结构化数据，停止调用并改用正文编号选项，不能发出残缺按钮。

开放题发出前检查：正文先用一两句解释为什么需要这个真实案例，然后只问“最近一次发生了什么”；不用示例继续索取人物、任务、耗时和后果。

## 宿主工具与降级

若宿主提供结构化提问工具，使用宿主的真实工具调用，而不是在正文里模拟按钮：

- WorkBuddy / Claude Code：使用可用的 `AskUserQuestion`；
- Codex 或其他 Agent：使用其等价的结构化提问工具；
- 工具不存在或当前线程不可调用：输出简短编号选项，让用户回复一个序号或一句自定义答案。

不要在技能中绑定某个工具的固定参数结构；不同宿主的字段和选项数量可能不同。

## 一句话开场示例

这些是路由示例，不是固定脚本。

### “我的公司怎么提升销售额？”

先解释：销售额通常由有效客户量、成交率、单笔价值与复购共同形成；四类问题需要不同证据，不能一律按“缺流量”处理。再定位当前最明显的缺口：潜在客户不足、联系后回应少、成交率低、单笔或复购不足。选择只决定下一步查哪段漏斗，不代表原因已经确认；“其他”使用宿主自带入口。

合格判断框架示例：销售额由有效客户量、回应、成交、单笔价值和复购共同形成，不同环节需要不同证据。先定位最明显的缺口，后续才能查对应环节；这只是调查入口，不代表根因已经确认。

### “我找不到客户，怎么扩大触达？”

先解释：客户触达至少包含识别对象、获得联系入口、得到回应和持续跟进；卡点不同，继续增加渠道可能有用，也可能只是放大无效触达。再区分：不知道目标客户在哪里、知道是谁但拿不到联系方式、能够联系但没有回应、触达后无法持续跟进。

合格判断框架示例：客户触达包含识别对象、获得联系入口、得到回应和持续跟进，卡在不同环节需要不同证据。先定位当前断点，避免把所有问题都归成渠道不足；这不是对根因的确认。

### “怎么把 AI 在组织里落地？”

先解释：AI 落地不是账号开通或培训完成，而是某类员工在真实任务上持续产生可验证结果；场景、采用、流程数据和组织机制是不同层次，后续判断与负责人都可能不同。再区分用户最想解决：找到首批业务场景、让员工真正使用、接入流程与知识数据、完善组织机制与治理。

合格判断框架示例：AI 落地要以真实任务中的持续结果衡量，而不只是账号或培训。业务场景、员工采用、流程数据和治理机制需要不同证据与负责人；先选入口，不代表已经诊断根因。

### “团队人太多，怎么管？”

先解释：单凭人数还不足以判断管理问题，真正需要定位的是规模扩大后出现的可观察后果；决策、协作、管理者带宽和权责绩效对应不同调查路径。再定位最想改善的后果：决策变慢、跨组协作混乱、管理者被日常事务淹没、职责与绩效不清。

合格判断框架示例：单凭人数不足以判断管理问题，关键是规模扩大后首先出现了什么可观察后果。决策、协作、管理者带宽和权责清晰度对应不同调查路径；先定位症状，不等于确认根因。

这些选项不能直接推导解决方案。后续仍需用具体案例和证据检查：用户选的是症状、猜测的原因，还是已经验证的判断。
